# Лекция 5. Базы данных и SQL

## 1. Зачем нужна база данных

Представим, что в прошлой лекции мы хранили задачи в обычной Go-мапе:

```
var tasks = map[int64]string{1:"Сделать домашку", 2:"Написать тесты"}
```

Это удобно для первого знакомства с HTTP, но у такого решения есть проблемы:

- После перезапуска процесса данные пропадут.
- Несколько экземпляров сервиса не будут автоматически разделять одни и те же данные.
- Придётся самим реализовывать поиск, фильтрацию, блокировки и ограничения целостности.
- Невозможно надёжно связать задачи с пользователями только с помощью слайса.

**База данных** — организованный набор данных. 
**СУБД** — программное обеспечение, которое управляет их хранением, чтением, изменением, конкурентным доступом и, в зависимости от системы, транзакциями.

База данных не обязана обладать всеми возможными свойствами сразу. Например, in-memory-хранилище может делать ставку на скорость, а PostgreSQL — на долговременное хранение, ограничения целостности и транзакционность.

Схема нашего приложения:

```text
HTTP-клиент (curl / браузер)
          |
          | HTTP / JSON
          v
     Go + Echo API
          |
          | pgxpool + SQL
          v
       PostgreSQL
      users / tasks
```

### Какие свойства нас интересуют

- **Сохранность данных:** задачи должны переживать перезапуск веб-сервера.
- **Конкурентный доступ:** разные клиенты могут одновременно читать и менять задачи.
- **Целостность:** `assignee_id` не должен указывать на отсутствующего пользователя.
- **Запросы:** нужно находить задачи по статусу, исполнителю, дате создания.
- **Транзакции:** несколько зависимых операций можно выполнить атомарно.

## 2. Основные типы баз данных

### 2.1. Реляционные базы данных

Данные хранятся в **таблицах**, строки представляют записи, а столбцы — атрибуты. Между таблицами можно задавать связи через внешние ключи. Для доступа к данным используется SQL.

Примеры: **PostgreSQL**, MySQL, SQLite.

**Преимущества:** связи между сущностями, декларативные запросы, ограничения целостности, транзакции, зрелая экосистема.

**Компромиссы:** изменение структуры таблиц требует миграций; сложные запросы и распределённое масштабирование нуждаются в отдельном проектировании.

### 2.2. Хранилища «ключ–значение»

Запись определяется ключом, а значение может быть строкой, числом, набором байт и т. п. Тот же `map[int64]string`, хотя реальные хранилища устроены гораздо сложнее.

Примеры: Redis, Valkey. Частое применение — кеш, счётчики, временное состояние.

**Плюсы:** простой доступ по ключу, быстрые операции в подходящих сценариях. 
**Минусы:** связи между сущностями и сложные выборки обычно надо организовывать отдельно.

### 2.3. Документные базы данных

Хранят документы (часто JSON-подобные) с неоднородной структурой. Примеры: MongoDB

Их удобно использовать там, где документы имеют разный набор полей, но гибкая схема не отменяет проектирования запросов и индексов.

### 2.4. Другие модели

Графовые, поисковые, временных рядов и специализированные аналитические БД. Разные задачи могут требовать разных хранилищ.

## 3. Реляционная модель на примере Task Tracker

Будем хранить две таблицы.

**`users`** — исполнители задач:

|  id | name  | email             |
| --: | ----- | ----------------- |
|   1 | Аня   | anna@example.com  |
|   2 | Борис | boris@example.com |

**`tasks`** — задачи:

|  id | title              | status      | assignee_id |
| --: | ------------------ | ----------- | ----------: |
|  10 | Подготовить лекцию | in_progress |           1 |
|  11 | Проверить тесты    | todo        |           2 |
|  12 | Обновить README    | done        |        NULL |


- **`PRIMARY KEY`** — первичный ключ: однозначно идентифицирует строку; PostgreSQL автоматически создаёт уникальный индекс для него.
- **`FOREIGN KEY`** — внешний ключ: `tasks.assignee_id` ссылается на `users.id`.
- **`NULL`** — отсутствие известного значения; не равно пустой строке и не равно числу `0`.

Схематично:

```text
users                             tasks
+-------------------+             +---------------------------+
| id (PK)           |             | assignee_id ( nullable)
| name              |    1 : N    | id (PK)                   |
| email (UNIQUE)    |             | title                     |
+-------------------+             | description               |
                                  | status                    |
                                  | created_at / updated_at   |
                                  +---------------------------+
```

### Зачем разделять `users` и `tasks`

Плохая схема: в каждую задачу записывать `assignee_name` и `assignee_email`. Тогда изменение email придётся повторять во множестве задач, появятся дубликаты и рассинхронизация.

Более удачная схема: хранить пользователя один раз, а в задаче — только его идентификатор. Это простой пример **нормализации**. В крупных системах денормализация иногда полезна для скорости чтения, но её делают осознанно.

### Основные типы PostgreSQL

| Тип             | Пример                        | Применение                                          |
| --------------- | ----------------------------- | --------------------------------------------------- |
| `BIGINT`        | `42`                          | Идентификатор, счётчик                              |
| `TEXT`          | `'todo'`                      | Заголовок, описание, статус                         |
| `BOOLEAN`       | `true`                        | Признак выполнения                                  |
| `TIMESTAMPTZ`   | Дата и время с часовым поясом | Время создания/изменения (хранение момента времени) |
| `NUMERIC(10,2)` | `125.50`                      | Точные десятичные значения                          |
| `UUID`          | `...`                         | Альтернатива числовым идентификаторам               |
| `JSONB`         | `{"a": 1}`                    | Дополнительные полуструктурированные данные         |

## 5. SQL: DDL и создание таблиц

SQL (Structured Query Language) — декларативный язык запросов. Мы описываем **что** получить или изменить, а СУБД выбирает способ выполнения.

Команды можно условно разделить на:

- **DDL:** `CREATE`, `ALTER`, `DROP` — описание структуры БД.
- **DML:** `INSERT`, `UPDATE`, `DELETE` — изменение строк.
- **DQL:** `SELECT` — выборка данных (иногда его включают в DML).


```sql
CREATE TABLE IF NOT EXISTS users (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name TEXT NOT NULL CHECK (char_length(btrim(name)) BETWEEN 1 AND 100),
    email TEXT NOT NULL UNIQUE
);

CREATE TABLE IF NOT EXISTS tasks (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    title TEXT NOT NULL CHECK (char_length(btrim(title)) BETWEEN 1 AND 200),
    description TEXT NOT NULL DEFAULT '',
    status TEXT NOT NULL DEFAULT 'todo'
        CHECK (status IN ('todo', 'in_progress', 'done')),
    assignee_id BIGINT REFERENCES users(id) ON DELETE SET NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX IF NOT EXISTS idx_tasks_assignee_id
    ON tasks (assignee_id);

CREATE INDEX IF NOT EXISTS idx_tasks_status_created_at
    ON tasks (status, created_at DESC);
```

Загрузим схему в базу (выполняем из папки с `schema.sql`):

```bash
docker exec -i task-tracker-db psql -U tracker -d tracker < schema.sql
```

Здесь есть важные элементы:

- `GENERATED ALWAYS AS IDENTITY` — идентификатор генерирует PostgreSQL.
- `NOT NULL` — значение обязательно.
- `DEFAULT` — значение по умолчанию (новая задача имеет `status = 'todo'`).
- `CHECK` — ограничение допустимых значений.
- `UNIQUE` — уникальность email.
- `REFERENCES users(id)` — внешний ключ.
- `ON DELETE SET NULL` — при удалении пользователя задача остаётся, но `assignee_id` становится `NULL`.
- `IF NOT EXISTS` — позволяет повторить создание отсутствующих объектов; это **не замена миграциям** при изменении существующей схемы.

## 6. CRUD-запросы на сыром SQL

Это примеры для `psql`. Сначала создадим двух исполнителей:

```sql
INSERT INTO users (name, email)
VALUES
    ('Аня', 'anna@example.com'),
    ('Борис', 'boris@example.com')
ON CONFLICT (email) DO NOTHING;
```

### 6.1. INSERT — добавление

```sql
INSERT INTO tasks (title, description, assignee_id)
VALUES (
    'Подготовить лекцию',
    'Составить примеры на Go и pgx',
    (SELECT id FROM users WHERE email = 'anna@example.com')
)
RETURNING id, title, status, assignee_id;
```

`RETURNING` возвращает вставленную строку без дополнительного `SELECT`.

### 6.2. SELECT — чтение

```sql
SELECT id, title, status
FROM tasks;
```

Выберем незавершённые задачи, сначала новые:

```sql
SELECT id, title, status, created_at
FROM tasks
WHERE status <> 'done'
ORDER BY created_at DESC
LIMIT 20;
```

### 6.3. WHERE, ORDER BY, LIMIT

- `WHERE` отбирает строки по условию.
- `ORDER BY` сортирует; `DESC` означает убывание.
- `LIMIT` ограничивает количество строк.
- `OFFSET` пропускает заданное число строк (для больших таблиц у такого способа пагинации бывают проблемы с производительностью).

### 6.4. UPDATE — обновление

```sql
UPDATE tasks
SET status = 'in_progress',
    updated_at = now()
WHERE id = 1;
```

**Без `WHERE` обновятся все строки!** 

### 6.5. DELETE — удаление

```sql
DELETE FROM tasks
WHERE id = 1;
```

**Без `WHERE` удалятся все строки!** Команда `DELETE` изменяет данные; `DROP TABLE` уничтожает сам объект таблицы.

### 6.6. JOIN — данные из нескольких таблиц

```sql
SELECT
    t.id,
    t.title,
    t.status,
    u.name AS assignee_name
FROM tasks AS t
LEFT JOIN users AS u ON t.assignee_id = u.id
ORDER BY t.id DESC;
```

Почему `LEFT JOIN`, а не `INNER JOIN`? Задачи без исполнителя (`assignee_id IS NULL`) тоже должны попадать в результат. `INNER JOIN` исключил бы такие строки.

### 6.7. GROUP BY — агрегирование

```sql
SELECT status, count(*) AS task_count
FROM tasks
GROUP BY status
ORDER BY status;
```

## 7. Индексы

Без подходящего индекса PostgreSQL может понадобиться проверить много строк, чтобы найти нужные записи.
**Индекс** — дополнительная структура данных, которая помогает выполнять определённые запросы быстрее.

Мы создали два индекса:

```sql
CREATE INDEX IF NOT EXISTS idx_tasks_assignee_id
ON tasks (assignee_id);

CREATE INDEX IF NOT EXISTS idx_tasks_status_created_at
ON tasks (status, created_at DESC);
```

Первый полезен при поиске задач исполнителя; второй может помочь при фильтрации по статусу и сортировке по времени. Эффективность зависит от размера таблицы, распределения значений и плана запроса — индекс не гарантирует ускорение любого `SELECT`.

Как посмотреть план выполнения:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, title
FROM tasks
WHERE status = 'todo'
ORDER BY created_at DESC
LIMIT 20;
```

`EXPLAIN ANALYZE` **выполняет запрос**, поэтому с изменяющими данными запросами его применяют осторожно. На маленькой таблице `Seq Scan` может оказаться эффективнее индекса — это нормально.

**Цена индекса:** место на диске, работа по его обновлению при `INSERT`, `UPDATE` и `DELETE`. Не нужно индексировать каждый столбец на всякий случай. Индекс на `PRIMARY KEY` PostgreSQL создаёт автоматически, но на `FOREIGN KEY` — **не обязательно**, поэтому `tasks.assignee_id` индексируем самостоятельно.
