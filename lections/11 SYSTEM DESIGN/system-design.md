# Лекция 11. Системный дизайн: распределённые системы и паттерны

## 1. Полезные свойства хранилищ

### ClickHouse

- Колоночная OLAP-БД: аналитика, агрегации и сканирование больших объёмов данных.
- Подходит для тяжёлых аналитических запросов и фоновых расчётов; также используется для интерактивной аналитики.
- Сжатие, пакетная загрузка, партиционирование, шардирование и репликация.

### S3

- Объектное хранилище: бакеты и объекты с ключами; доступ по HTTP API.
- Подходит для файлов, снимков данных, резервных копий и статики; удобно использовать вместе с CDN.
- Масштабирование больших объёмов хранения; стоимость зависит от объёма, запросов и передачи данных.
- Версионирование, lifecycle-политики, классы хранения и репликация.
- Presigned URL для временного доступа; multipart upload для больших объектов.
- Amazon S3: строгая согласованность чтения после записи; гарантии S3-совместимых реализаций нужно уточнять.

## 2. Распределённые транзакции и консенсус

### Saga

- Бизнес-операция как последовательность локальных транзакций в нескольких сервисах.
- При сбое завершённые шаги при необходимости компенсируются отдельными бизнес-операциями.
- Оркестровка. Координатор хранит состояние саги и управляет шагами и компенсациями.
- Хореография. Сервисы реагируют на события друг друга и запускают следующие шаги.
- Промежуточные состояния видны. Повторы шагов и компенсаций требуют идемпотентности.

### Transactional outbox

- Изменение данных и запись исходящего события сохраняются в одной транзакции БД.
- Отдельный процесс читает outbox через опрос таблицы или CDC и публикует события.
- Повторная публикация возможна. Обработчик устраняет дубли или выполняет операцию идемпотентно.

### 2PC (двухфазная фиксация)

- Prepare. Координатор спрашивает участников, готовы ли они зафиксировать транзакцию.
- Commit или rollback. Координатор фиксирует решение о коммите, если все участники готовы, иначе выбирает откат.
- Подготовленные участники могут удерживать блокировки, пока ждут итоговое решение.

### Raft

- Алгоритм консенсуса для репликации журнала команд.
- Узлы выбирают лидера большинством голосов. Лидер принимает команды и отправляет записи репликам.
- Лидер фиксирует запись текущего срока после её репликации на большинство узлов.
- Без большинства кластер не может фиксировать новые записи.

## 3. Event Sourcing и CQRS

### Event Sourcing

- Источник истины — упорядоченный журнал неизменяемых событий предметной области.
- Текущее состояние получаем, последовательно применяя события. Снимки ускоряют восстановление.
- Из журнала можно заново собрать проекции и восстановить состояние на нужный момент.
- Нужно продумать версии событий и стоимость повторной обработки истории.

### CQRS

- Раздельные модели для записи и чтения.
- Команды проверяют бизнес-правила и меняют состояние. Запросы читают данные в удобном для клиента виде.
- Обе модели могут использовать одну БД. Отдельное хранилище чтения позволяет масштабировать его независимо.
- При асинхронном обновлении проекций чтение может отставать от записи.
- Event Sourcing и CQRS можно применять вместе или по отдельности.

## 4. Монолит и микросервисы

### Идеализированный монолит

- Один репозиторий, одна общая БД, один пайплайн CI/CD.
- Все модули компилируются в один большой бинарник и выкатываются вместе.
  По мере роста кодовой базы полная сборка может занимать больше времени.
- Модули вызывают друг друга внутри процесса.
  Изменения в нескольких модулях можно провести одной транзакцией в общей БД.
- При росте нагрузки масштабируем всё приложение. Сбой процесса затрагивает все его модули.

### Идеализированные микросервисы

- Каждый сервис отвечает за свою бизнес-область и владеет своими данными.
- У каждого сервиса свой репозиторий, пайплайн CI/CD и БД или выделенный кластер БД.
- Сервисы собираются, выкатываются и масштабируются независимо.
- Сервисы взаимодействуют через сетевые API и события.
  Нужно учитывать частичные сбои, повторы и согласованность данных.
- Отдельные сервисы требуют больше инфраструктуры, наблюдаемости и сопровождения.

В реальных проектах микросервисы могут жить в монорепозитории. Их границы определяют владение данными
и возможность независимо развёртывать сервисы.

## 5. Задача: высоконагруженный геораспределённый сервис сокращения ссылок

Необходимо разработать сервис, который принимает длинный URL, генерирует короткую ссылку
и перенаправляет пользователей на оригинальный адрес.

Например: `https://example.com/very/long/path` → `https://sho.rt/aB3xYz1`.

### Функциональные требования

- Создание короткой ссылки по HTTP API.
- Редирект по короткой ссылке.
- Уникальность кодов.
- Ссылки бессрочные и не изменяются.
- Идемпотентность создания по ключу клиента.
- Базовая валидация URL.

Не требуются: авторизация, удаление ссылок, пользовательские алиасы, истечение срока действия.

### Нефункциональные требования

| Параметр | Требование |
| --- | --- |
| Всего ссылок | 100 млн |
| Создание, среднее | 200 RPS |
| Создание, пик | 1 000 RPS |
| Редиректы, среднее | 10 000 RPS |
| Редиректы, пик | 50 000 RPS |
| Latency редиректа | P95 < 50 мс |
| Доступность | 99,9%+ |
| География | Весь мир |
| Формат кода | Base62, 7 символов |
| Распределение нагрузки | 1% ссылок дают 80–90% кликов |

<details>
<summary>Решение</summary>

Разделяем создание и чтение: запись направляем в один основной регион,
а редиректы обслуживаем в ближайшем к пользователю регионе через CDN и региональные кеши.
Это один из вариантов архитектуры, который нужно проверить нагрузочными тестами.

**Хранение и коды.** PostgreSQL хранит неизменяемые соответствия `code → URL`.
Генерируем случайный семисимвольный Base62-код, пробуем вставить его с уникальным ограничением на `code`.
При коллизии повторяем генерацию. Пространство кодов: `62^7 ≈ 3,52 трлн`;
при 100 млн записей занято около 0,0028%, но проверка уникальности всё равно обязательна.
При условных 500 байтах на запись получаем около 50 ГБ данных без индексов и реплик.
Одна БД — исходная точка; шардирование добавляем по результатам измерений.

**Создание.** `POST /links` принимает URL и `Idempotency-Key`.
Проверяем корректность URL, наличие хоста, схему `http` или `https` и ограничение длины.
В одной транзакции сохраняем ссылку и соответствие ключа идемпотентности запросу и результату.
На ключе стоит уникальное ограничение: конкурентные повторы получают один и тот же результат.
Повтор ключа с другим URL возвращает конфликт. Успех отвечаем после надёжной фиксации транзакции.

**Редирект.** `GET /{code}` ищет результат последовательно в CDN, локальном кеше процесса,
региональном Redis и региональной реплике БД.
Возвращаем `301` с заголовком `Location` и явной политикой кеширования.
Поскольку ссылки не меняются, положительные результаты можно кешировать надолго.
Горячие ссылки распределяются по CDN и кешам экземпляров приложения, снижая нагрузку на Redis и БД.

**География и свежие ссылки.** Реплики в других регионах обновляются асинхронно.
При отсутствии кода в региональной реплике проверяем основную БД;
если она недоступна, не выдаём отсутствие ссылки за достоверный `404`.
Так новая ссылка работает до завершения репликации, но её первый редирект может быть медленнее.
P95 < 50 мс уточняем по точке измерения и проверяем отдельно по регионам:
близость кешей помогает достичь цели, но не гарантирует её сама по себе.

**Доступность.** Запускаем несколько экземпляров приложений и отказоустойчивые хранилища.
При недоступности основного региона кеши и региональные реплики продолжают обслуживать известные ссылки.
Создание и чтение ещё не реплицированных ссылок требуют отдельной политики восстановления.
Для отказа узла в основном регионе используем синхронную реплику и управляемое переключение без двух писателей.
Целевые доступность, RPO и RTO при потере целого региона согласуем отдельно.

</details>

<details>
<summary>Дополнения и вопросы для обсуждения</summary>

- Уточнить, включает ли latency DNS, TLS и сеть клиента или только обработку на стороне сервиса.
  Уточнить период и отдельные SLO для создания и редиректов.
- 100 млн ссылок — текущий объём или предел? При постоянных 200 созданиях в секунду
  добавляется 17,28 млн ссылок в сутки. Бессрочное хранение требует оценки роста на годы.
- Без авторизации ключ идемпотентности должен быть глобально уникальным, например случайным UUID.
  Срок хранения ключей определяет срок гарантии идемпотентности; он требует отдельной договорённости.
- Отрицательные ответы не стоит кешировать надолго: можно скрыть только что созданную ссылку.
  При недоступности источника истины возвращаем временную ошибку, а не кешируем ложный `404`.
- Одновременные промахи по горячей ссылке объединяем в один запрос к хранилищу;
  при отказе Redis ограничиваем поток запросов в БД, чтобы не вызвать каскадный отказ.
- При восстановлении из резервной копии нельзя переиспользовать коды потерянных подтверждённых ссылок.
  Резервные копии и репликация решают разные задачи; нужны проверяемые процедуры восстановления.
- Если требуется запись в нескольких регионах, глобальную идемпотентность всё равно нужно согласовать.
  Раздельные диапазоны кодов решают уникальность, но не обработку одного ключа в разных регионах.
- Межрегиональная синхронная запись уменьшает риск потери данных, но увеличивает latency
  и может ограничить доступность записи при сетевом разделении. Это явный компромисс требований.
- При `301` браузер может обслужить повторный переход из своего кеша;
  точный подсчёт всех кликов потребовал бы отдельного обсуждения, но в условии аналитики нет.
- Короткая ссылка не является секретом. Базовая валидация URL не гарантирует безопасность сайта назначения.
  Для редиректа не нужно скачивать содержимое исходного адреса на backend.

</details>
